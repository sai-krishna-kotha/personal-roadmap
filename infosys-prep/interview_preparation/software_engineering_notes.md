Software Engineering Overview\n<a id="software-engineering-overview"></a>\n\nSoftware engineering is the disciplined process of understanding a problem, designing software, implementing it, testing it, deploying it, operating it and maintaining it.\n\nThink:\n`Requirement -> Design -> Code -> Test -> Review -> Build -> Deploy -> Monitor -> Maintain`\n\n**Interview line:** "Software engineering is not only coding; it covers the complete software lifecycle from requirements through maintenance."\n\n[Back to Table of Contents](#table-of-contents)\n\n## 2. SDLC\n<a id="sdlc"></a>\n\nSDLC means **Software Development Life Cycle**.\n\nTypical activities:\n\n`Requirement gathering -> Analysis -> Design -> Implementation -> Testing -> Deployment -> Maintenance`\n\nModern teams often repeat these activities iteratively rather than treating them as one rigid sequence.\n\n**Example:** A ScoreHub feature goes from requirement, to API/database design, implementation, testing, deployment and monitoring.\n\n[Back to Table of Contents](#table-of-contents)\n\n## 3. SDLC Models\n<a id="sdlc-models"></a>\n\n### Waterfall\nSequential phases with heavy upfront planning. Useful when requirements are stable and change is costly.\n\n### Iterative\nBuild a version, learn from it, then improve it.\n\n### Incremental\nDeliver the product in usable pieces.\n\n### Spiral\nRepeated cycles with explicit risk analysis.\n\n### Agile\nIterative delivery with frequent feedback and adaptation.\n\n**Interview point:** Waterfall emphasizes sequential planning; Agile emphasizes iterative delivery and adaptation.\n\n[Back to Table of Contents](#table-of-contents)\n\n## 4. Agile and Scrum\n<a id="agile-and-scrum"></a>\n\nScrum commonly defines:\n\n- Roles/accountabilities: Product Owner, Scrum Master, Developers\n- Artifacts: Product Backlog, Sprint Backlog, Increment\n- Events: Sprint, Sprint Planning, Daily Scrum, Sprint Review, Sprint Retrospective\n\n**Trap:** Agile is broader than Scrum. Scrum is a specific framework.\n\n**Practical example:** A two-week sprint can deliver login, URL creation, analytics and tests.\n\n[Back to Table of Contents](#table-of-contents)\n\n## 5. Requirements Engineering\n<a id="requirements-engineering"></a>\n\nRequirements engineering means discovering, analyzing, documenting and validating what a system must do and the constraints under which it must operate.\n\nActivities:\n`Elicitation -> Analysis -> Specification -> Validation -> Management`\n\nAsk:\n- What does the user need?\n- What constraints exist?\n- What happens on failure?\n- What scale is expected?\n- What security requirements exist?\n\n[Back to Table of Contents](#table-of-contents)\n\n## 6. Functional vs Non-Functional Requirements\n<a id="functional-vs-non-functional-requirements"></a>\n\n**Functional requirement:** what the system does.\n\nExample: `POST /scenes` creates a scene.\n\n**Non-functional requirement:** a quality attribute or constraint.\n\nExamples: latency target, availability, security, scalability.\n\n**Interview line:** "Functional requirements describe behavior; non-functional requirements describe quality attributes and constraints."\n\n[Back to Table of Contents](#table-of-contents)\n\n## 7. User Stories and Acceptance Criteria\n<a id="user-stories-and-acceptance-criteria"></a>\n\nTypical user story:\n\n> As a user, I want to create a short URL so that I can share it easily.\n\nAcceptance criteria define when the story is complete.\n\nExample:\n- Valid URL returns a short code.\n- Invalid URL returns a validation error.\n- Short code redirects correctly.\n- Duplicate handling follows the documented rule.\n\n[Back to Table of Contents](#table-of-contents)\n\n## 8. Software Architecture Styles\n<a id="software-architecture-styles"></a>\n\nKnow:\n- Layered architecture\n- Monolithic architecture\n- Modular monolith\n- Microservices\n- Service-oriented architecture\n- Event-driven architecture\n- Client-server\n- Hexagonal / ports-and-adapters\n\nChoose based on team size, domain boundaries, deployment independence, scaling, failure isolation, data ownership and operational complexity.\n\n[Back to Table of Contents](#table-of-contents)\n\n## 9. Monolith vs Modular Monolith vs Microservices\n<a id="monolith-vs-modular-monolith-vs-microservices"></a>\n\n**Monolith:** one deployable application.\n\n**Modular monolith:** one deployable application with explicit internal module boundaries.\n\n**Microservices:** multiple independently deployable services, usually aligned to business capabilities.\n\n**Interview point:** Microservices can improve independent deployment and scaling, but add network failures, observability, service discovery and data-consistency complexity.\n\n[Back to Table of Contents](#table-of-contents)\n\n## 10. Service-Oriented and Event-Driven Architecture\n<a id="service-oriented-and-event-driven-architecture"></a>\n\n**Service-oriented architecture:** applications are composed of services exposing functionality to other services.\n\n**Event-driven architecture:** producers emit events and consumers react asynchronously.\n\nExample:\n`OrderCreated -> payment -> inventory -> notification`\n\n[Back to Table of Contents](#table-of-contents)\n\n## 11. APIs: What They Are\n<a id="apis-what-they-are"></a>\n\nAn API is a defined interface through which one software component communicates with another.\n\nThink:\n`Caller -> Contract -> Provider -> Result`\n\nThe contract defines operations, inputs, outputs, errors, authentication and semantics.\n\nExamples:\n- Browser -> FastAPI\n- React -> backend\n- FastAPI -> external provider\n- Python application -> library\n\n**Key point:** An API is broader than REST and does not require HTTP.\n\n[Back to Table of Contents](#table-of-contents)\n\n## 12. API Styles and Types\n<a id="api-styles-and-types"></a>\n\n| Type | Main idea | Typical use |\n|---|---|---|\n| REST | Resource-oriented HTTP API | General web/backend APIs |\n| SOAP | XML-based protocol with formal standards | Enterprise integrations |\n| GraphQL | Client asks for required fields | Flexible data fetching |\n| gRPC | RPC with commonly HTTP/2 + Protobuf | Internal service-to-service calls |\n| WebSocket | Persistent bidirectional connection | Real-time systems |\n| Webhook | HTTP callback triggered by an event | External event notifications |\n| Library/SDK API | In-process programming interface | Reusable code |\n\n**Interview line:** "REST and GraphQL are common application API styles; gRPC is RPC; WebSockets solve persistent real-time communication; webhooks are callbacks; a library API can be entirely in-process."\n\n[Back to Table of Contents](#table-of-contents)\n\n## 13. REST API\n<a id="rest-api"></a>\n\nREST is an architectural style for networked applications.\n\nCommon ideas:\n- resource-oriented URLs\n- HTTP methods\n- stateless requests\n- representations such as JSON\n- standard HTTP semantics\n\nExample:\n\n```text\nGET /users/42\nPOST /users\nPATCH /users/42\nDELETE /users/42\n```\n\nKnow safe methods, idempotency, status codes, pagination, versioning and caching.\n\n[Back to Table of Contents](#table-of-contents)\n\n## 14. SOAP API\n<a id="soap-api"></a>\n\nSOAP is a protocol for structured messages, commonly represented as XML.\n\nKnow:\n- Envelope\n- Header\n- Body\n- WSDL\n- XML schema\n- enterprise extensions\n\n**Practical example:** a legacy enterprise or banking integration can expose a SOAP operation described by WSDL.\n\n**Interview point:** REST is usually simpler and resource-oriented; SOAP provides a formal protocol and enterprise standards ecosystem.\n\n[Back to Table of Contents](#table-of-contents)\n\n## 15. GraphQL API\n<a id="graphql-api"></a>\n\nGraphQL lets clients request the fields they need through a schema.\n\n```graphql\nquery {\n  user(id: "42") {\n    name\n    email\n    projects { name }\n  }\n}\n```\n\nStrengths:\n- flexible response shape\n- can reduce under-fetching\n- strong schema\n\nChallenges:\n- resolver complexity\n- field-level authorization\n- caching complexity\n- query-cost / abuse concerns\n\n**Interview line:** "GraphQL gives clients control over the response shape, while REST commonly exposes resource-oriented endpoints."\n\n[Back to Table of Contents](#table-of-contents)\n\n## 16. gRPC API\n<a id="grpc-api"></a>\n\ngRPC is an RPC framework commonly using HTTP/2 and Protocol Buffers.\n\nExample:\n\n```protobuf\nservice UserService {\n  rpc GetUser(GetUserRequest) returns (User);\n}\n```\n\nWhy use it?\n- efficient binary serialization\n- generated strongly typed clients\n- strong service contracts\n- streaming support\n\n**Interview point:** gRPC is often attractive for internal service-to-service communication where performance and strict contracts matter.\n\n[Back to Table of Contents](#table-of-contents)\n\n## 17. WebSocket API\n<a id="websocket-api"></a>\n\nWebSocket establishes a persistent, bidirectional communication channel.\n\nHTTP:\n`Client -> request -> Server -> response`\n\nWebSocket:\n`Client <-> persistent connection <-> Server`\n\nExamples: chat, live sports, notifications, collaborative editing.\n\n**ScoreHub:** a browser can subscribe to a match and receive score updates without repeated polling.\n\n**Trap:** WebSockets are not simply "faster REST"; they solve a different communication pattern.\n\n[Back to Table of Contents](#table-of-contents)\n\n## 18. Webhooks\n<a id="webhooks"></a>\n\nA webhook is an HTTP callback sent by one system to another when an event occurs.\n\nExample:\n`Payment provider -> POST /webhooks/payment -> your backend`\n\nReceiver should usually:\n1. verify authenticity\n2. validate payload\n3. handle duplicate delivery\n4. acknowledge quickly\n5. process asynchronously when appropriate\n\n**Key point:** Webhooks are usually push notifications between systems.\n\n[Back to Table of Contents](#table-of-contents)\n\n## 19. Library / SDK APIs\n<a id="library-sdk-apis"></a>\n\nAn API does not have to be a network endpoint.\n\n```python\nfrom datetime import datetime\nnow = datetime.now()\n```\n\nAn SDK may expose:\n`client.create_payment(...)`\n\n**Interview point:** API means interface/contract; HTTP is only one way to expose an API.\n\n[Back to Table of Contents](#table-of-contents)\n\n## 20. API Comparison\n<a id="api-comparison"></a>\n\n| Technology | Mechanism | Typical use |\n|---|---|---|\n| REST | HTTP | General web APIs |\n| SOAP | Structured protocol, commonly XML over HTTP | Enterprise integrations |\n| GraphQL | Schema/query API, commonly over HTTP | Flexible client data fetching |\n| gRPC | RPC, commonly HTTP/2 + Protobuf | Internal services |\n| WebSocket | Persistent connection | Real-time bidirectional communication |\n| Webhook | HTTP callback | Event notification |\n| SDK/Library API | In-process call | Reusable functionality |\n\nThese can coexist in one architecture.\n\nExample:\n`REST externally + gRPC internally + WebSocket for live updates + webhooks for provider events`\n\n[Back to Table of Contents](#table-of-contents)\n\n## 21. REST Interview Essentials\n<a id="rest-interview-essentials"></a>\n\nHTTP methods:\n- `GET`: retrieve\n- `POST`: create or trigger processing\n- `PUT`: replace a resource\n- `PATCH`: partially modify\n- `DELETE`: remove\n\nCommon statuses:\n- `200 OK`\n- `201 Created`\n- `204 No Content`\n- `400 Bad Request`\n- `401 Unauthorized`\n- `403 Forbidden`\n- `404 Not Found`\n- `409 Conflict`\n- `422 Unprocessable Content`\n- `429 Too Many Requests`\n- `500 Internal Server Error`\n- `503 Service Unavailable`\n\n**Trap:** `401` and `403` are not interchangeable.\n\n[Back to Table of Contents](#table-of-contents)\n\n## 22. API Design Essentials\n<a id="api-design-essentials"></a>\n\nGood API design includes:\n- clear resource naming\n- predictable request/response contracts\n- validation\n- meaningful errors\n- consistent status codes\n- authentication/authorization\n- pagination\n- idempotency where needed\n- a versioning strategy\n- documentation\n- backward compatibility\n\nExample:\n`GET /users/42` is clearer as a resource API than `/getUserById?id=42`.\n\n[Back to Table of Contents](#table-of-contents)\n\n## 23. API Versioning\n<a id="api-versioning"></a>\n\nVersioning protects consumers from breaking changes.\n\nCommon approach:\n`/api/v1/users`\n\nBreaking changes include removing a field, changing its type, changing semantics or removing an endpoint.\n\n**Interview point:** Prefer additive, backward-compatible changes when possible.\n\n[Back to Table of Contents](#table-of-contents)\n\n## 24. Pagination, Filtering, Sorting and Searching\n<a id="pagination-filtering-sorting-and-searching"></a>\n\nDo not return huge collections in one response.\n\nOffset:\n`GET /users?page=3&limit=20`\n\nCursor:\n`GET /users?cursor=abc&limit=20`\n\nFiltering:\n`GET /orders?status=paid`\n\nSorting:\n`GET /users?sort=-created_at`\n\n**Interview point:** Pagination affects both API design and database query performance.\n\n[Back to Table of Contents](#table-of-contents)\n\n## 25. API Error Handling\n<a id="api-error-handling"></a>\n\nUse stable, machine-readable errors.\n\n```json\n{\n  "error": {\n    "code": "INVALID_URL",\n    "message": "The URL is invalid",\n    "details": {"field": "url"}\n  }\n}\n```\n\nGood practice:\n- stable error code\n- useful message\n- no secrets or internal stack traces\n- request/correlation ID when useful\n\n[Back to Table of Contents](#table-of-contents)\n\n## 26. Idempotency\n<a id="idempotency"></a>\n\nAn operation is idempotent when repeating it has the same intended effect as doing it once.\n\nExample:\n`Idempotency-Key: 8f0...`\n\nA retry-safe payment API can store the result for that key and avoid charging twice.\n\n**Interview point:** Idempotency is critical because networks fail and clients retry.\n\n[Back to Table of Contents](#table-of-contents)\n\n## 27. Authentication vs Authorization\n<a id="authentication-vs-authorization"></a>\n\n**Authentication:** Who are you?\n\n**Authorization:** What are you allowed to do?\n\nExample: login verifies identity; RBAC determines whether the user can delete a project.\n\n[Back to Table of Contents](#table-of-contents)\n\n## 28. Sessions, JWT and OAuth2\n<a id="sessions-jwt-and-oauth2"></a>\n\n**Session authentication:** server stores session state; client sends an identifier.\n\n**JWT:** a signed token carries claims that a server can validate. Expiration, revocation/rotation and storage still matter.\n\n**OAuth2:** an authorization framework for delegated access.\n\n**Trap:** OAuth2 is primarily an authorization framework, not simply a login technology.\n\n[Back to Table of Contents](#table-of-contents)\n\n## 29. RBAC and Access Control\n<a id="rbac-and-access-control"></a>\n\nRBAC = Role-Based Access Control.\n\nExample:\n- admin: create/update/delete\n- editor: create/update\n- viewer: read\n\nOther authorization models use scopes, permissions or attributes/policies.\n\n[Back to Table of Contents](#table-of-contents)\n\n## 30. API Security\n<a id="api-security"></a>\n\nKnow:\n- HTTPS/TLS\n- authentication\n- authorization\n- input validation\n- rate limiting\n- secret management\n- secure password hashing\n- safe error responses\n- audit logging\n- least privilege\n- dependency patching\n\nNever hard-code secrets into source control.\n\n[Back to Table of Contents](#table-of-contents)\n\n## 31. CORS, CSRF and XSS\n<a id="cors-csrf-and-xss"></a>\n\n**CORS:** browser mechanism controlling allowed cross-origin requests.\n\n**CSRF:** attacker causes a user's browser to send an unwanted authenticated request.\n\n**XSS:** attacker-controlled script executes in a victim's browser.\n\nMitigations include correct CORS policy, CSRF tokens/SameSite cookies, output encoding, safe templating and content security policy where applicable.\n\n**Trap:** CORS is not an authentication mechanism.\n\n[Back to Table of Contents](#table-of-contents)\n\n## 32. Testing Fundamentals\n<a id="testing-fundamentals"></a>\n\nTesting checks whether software behaves as expected, including boundaries and failure cases.\n\nGood test thinking covers:\n- happy path\n- edge cases\n- invalid inputs\n- dependency failures\n- concurrency risks\n- regression prevention\n\n[Back to Table of Contents](#table-of-contents)\n\n## 33. Testing Levels\n<a id="testing-levels"></a>\n\nCommon levels:\n- Unit\n- Integration\n- System\n- Acceptance / end-to-end\n\nOrganizations may use slightly different terminology.\n\n[Back to Table of Contents](#table-of-contents)\n\n## 34. Testing Types\n<a id="testing-types"></a>\n\nKnow:\n- Functional\n- Regression\n- Smoke\n- Sanity\n- Performance\n- Load\n- Stress\n- Security\n- Usability\n- Compatibility\n\nSmoke asks whether the build is stable enough for deeper testing.\n\nRegression asks whether a change broke existing behavior.\n\n[Back to Table of Contents](#table-of-contents)\n\n## 35. Test Cases and Test Strategy\n<a id="test-cases-and-test-strategy"></a>\n\nA test case usually records preconditions/input, steps, expected result, actual result and pass/fail.\n\nTest strategy defines the overall approach.\n\nURL shortener cases:\n- valid URL\n- invalid URL\n- empty URL\n- duplicate request\n- existing redirect\n- missing redirect\n- expired link\n- concurrent creation\n\n[Back to Table of Contents](#table-of-contents)\n\n## 36. Unit vs Integration vs E2E\n<a id="unit-vs-integration-vs-e2e"></a>\n\n**Unit:** small component in isolation.\n\n**Integration:** interaction between components, such as FastAPI + PostgreSQL.\n\n**E2E:** complete flow, such as Browser -> API -> DB -> response.\n\nUnit tests are usually faster and less brittle; E2E tests provide broader confidence but are generally more expensive.\n\n[Back to Table of Contents](#table-of-contents)\n\n## 37. Contract Testing\n<a id="contract-testing"></a>\n\nContract testing checks that communicating systems agree on an API contract.\n\nExample: if consumers expect an integer `id` and a provider changes it to a string, contract tests can detect the breaking change.\n\nUseful when many services evolve independently.\n\n[Back to Table of Contents](#table-of-contents)\n\n## 38. Git and Version Control\n<a id="git-and-version-control"></a>\n\nKnow:\n`clone, status, add, commit, pull, push, branch, merge, rebase, stash, cherry-pick, revert, reset`\n\nImportant difference:\n- `git revert` creates a new commit that undoes an earlier commit.\n- `git reset` moves the branch pointer and can rewrite history.\n\n[Back to Table of Contents](#table-of-contents)\n\n## 39. Git Workflows\n<a id="git-workflows"></a>\n\nCommon approaches:\n- feature branches with code review\n- trunk-based development with frequent small integrations\n\nChoose based on team practices, release model and deployment process.\n\n[Back to Table of Contents](#table-of-contents)\n\n## 40. Code Review\n<a id="code-review"></a>\n\nReview for:\n- correctness\n- readability\n- design\n- tests\n- security\n- performance when relevant\n- maintainability\n\nExample review comment:\n> Can this operation be made idempotent? The client may retry after a timeout.\n\n[Back to Table of Contents](#table-of-contents)\n\n## 41. CI and CD\n<a id="ci-and-cd"></a>\n\n**Continuous Integration:** frequently integrate changes and automatically validate them.\n\n**Continuous Delivery:** keep software in a deployable state.\n\n**Continuous Deployment:** automatically deploy qualifying changes to production.\n\n**Trap:** Delivery and Deployment are not identical.\n\n[Back to Table of Contents](#table-of-contents)\n\n## 42. CI/CD Pipeline\n<a id="cicd-pipeline"></a>\n\nTypical pipeline:\n`Commit -> lint -> unit tests -> integration tests -> security checks -> build -> artifact -> deploy -> smoke tests`\n\nGitHub Actions can run these steps automatically.\n\n[Back to Table of Contents](#table-of-contents)\n\n## 43. Environments and Configuration\n<a id="environments-and-configuration"></a>\n\nTypical environments:\n- development\n- testing\n- staging\n- production\n\nConfiguration includes database URLs, Redis URLs, API keys, feature flags and logging levels.\n\nKeep configuration outside source code and store secrets securely.\n\n[Back to Table of Contents](#table-of-contents)\n\n## 44. Docker and Deployment Basics\n<a id="docker-and-deployment-basics"></a>\n\nDocker packages an application and its dependencies into an image.\n\nFlow:\n`Code -> Docker image -> registry -> deployment platform -> container`\n\nKnow image vs container, Dockerfile, ports, environment variables, volumes, health checks and container networking.\n\n**Trap:** Docker does not by itself solve orchestration, scaling or observability.\n\n[Back to Table of Contents](#table-of-contents)\n\n## 45. Release Strategies\n<a id="release-strategies"></a>\n\n- **Rolling:** replace instances gradually.\n- **Blue-green:** keep old and new environments and switch traffic.\n- **Canary:** send a small amount of traffic to the new version first.\n- **Feature flag:** deploy code but control exposure separately.\n\n[Back to Table of Contents](#table-of-contents)\n\n## 46. Code Quality Principles\n<a id="code-quality-principles"></a>\n\nKnow:\n- SOLID\n- DRY\n- KISS\n- YAGNI\n- separation of concerns\n- high cohesion\n- low coupling\n- dependency inversion\n- readable naming\n- focused functions\n\nYour OOP and LLD notes cover these deeply; this file connects them to daily software engineering.\n\n[Back to Table of Contents](#table-of-contents)\n\n## 47. DRY, KISS, YAGNI and Separation of Concerns\n<a id="dry-kiss-yagni-and-separation-of-concerns"></a>\n\n**DRY:** avoid duplicated knowledge or logic.\n\n**KISS:** prefer the simplest design that satisfies requirements.\n\n**YAGNI:** do not build speculative functionality before it is needed.\n\n**Separation of concerns:** keep responsibilities distinct.\n\nExample:\n`Router -> Service -> Repository`\n\n[Back to Table of Contents](#table-of-contents)\n\n## 48. Coupling and Cohesion\n<a id="coupling-and-cohesion"></a>\n\n**High cohesion:** responsibilities inside a module belong together.\n\n**Low coupling:** modules depend on each other as little as reasonably possible.\n\n**Interview line:** Good design generally aims for high cohesion and low coupling.\n\n[Back to Table of Contents](#table-of-contents)\n\n## 49. Documentation\n<a id="documentation"></a>\n\nUseful engineering documents:\n- README\n- API specification\n- architecture document\n- deployment guide\n- runbook\n- troubleshooting guide\n- decision record\n\nGood documentation answers: What? Why? How? How to run? What can fail?\n\n[Back to Table of Contents](#table-of-contents)\n\n## 50. UML and Engineering Diagrams\n<a id="uml-and-engineering-diagrams"></a>\n\nKnow the purpose of:\n- class diagram\n- sequence diagram\n- component diagram\n- deployment diagram\n- activity diagram\n- state diagram\n\nA sequence diagram is especially useful for request flows:\n`Client -> API -> Service -> DB -> API -> Client`\n\n[Back to Table of Contents](#table-of-contents)\n\n## 51. Logging\n<a id="logging"></a>\n\nLogs should provide useful operational context such as timestamp, severity, service and request/correlation ID.\n\nExample:\n`request_id=abc123 route=/shorten status=201 duration_ms=18`\n\nDo not log passwords, access tokens or sensitive information.\n\n[Back to Table of Contents](#table-of-contents)\n\n## 52. Monitoring and Metrics\n<a id="monitoring-and-metrics"></a>\n\nImportant metrics:\n- request rate\n- latency\n- error rate\n- CPU\n- memory\n- queue depth\n- database connections\n\nKnow p50, p95 and p99 latency. Tail latency can matter more than the average.\n\n[Back to Table of Contents](#table-of-contents)\n\n## 53. Observability and Tracing\n<a id="observability-and-tracing"></a>\n\nObservability commonly uses logs, metrics and traces.\n\nDistributed tracing follows a request through services:\n`API -> auth -> order -> payment -> DB`\n\n**Interview line:** Monitoring tells you that something is wrong; observability helps investigate why.\n\n[Back to Table of Contents](#table-of-contents)\n\n## 54. Reliability Patterns\n<a id="reliability-patterns"></a>\n\nKnow:\n- timeout\n- retry\n- exponential backoff\n- jitter\n- circuit breaker\n- bulkhead\n- idempotency\n- rate limiting\n- graceful degradation\n- health checks\n\nDistributed components can fail independently, so design for partial failure.\n\n[Back to Table of Contents](#table-of-contents)\n\n## 55. Timeouts, Retries and Circuit Breakers\n<a id="timeouts-retries-and-circuit-breakers"></a>\n\n**Timeout:** do not wait forever.\n\n**Retry:** repeat a failed request when retrying is safe and useful. Use exponential backoff and jitter.\n\n**Circuit breaker:** temporarily stop calling a failing dependency after repeated failures.\n\n**Trap:** retries can amplify outages and can duplicate non-idempotent operations.\n\n[Back to Table of Contents](#table-of-contents)\n\n## 56. Graceful Shutdown and Health Checks\n<a id="graceful-shutdown-and-health-checks"></a>\n\n**Graceful shutdown:** stop new work and safely handle in-flight work according to policy.\n\n**Liveness:** is the process alive?\n\n**Readiness:** can this instance receive traffic?\n\nThese are different questions.\n\n[Back to Table of Contents](#table-of-contents)\n\n## 57. Performance Engineering\n<a id="performance-engineering"></a>\n\nWorkflow:\n`Measure -> identify bottleneck -> change -> measure again`\n\nPossible bottlenecks: CPU, I/O, network, database queries, serialization and lock contention.\n\nDo not optimize based only on intuition.\n\n[Back to Table of Contents](#table-of-contents)\n\n## 58. Load Testing\n<a id="load-testing"></a>\n\nKnow:\n- **Load:** expected workload\n- **Stress:** beyond expected capacity\n- **Spike:** sudden traffic increase\n- **Soak:** long-duration workload\n\nMeasure throughput, latency, error rate and resource usage.\n\n[Back to Table of Contents](#table-of-contents)\n\n## 59. Caching and Performance\n<a id="caching-and-performance"></a>\n\nCaching stores frequently needed data closer to consumers.\n\nExamples: browser cache, CDN, reverse proxy, Redis, application memory.\n\nImportant concerns:\n- TTL\n- invalidation\n- stale data\n- cache stampede\n- eviction policy\n\n**Interview line:** Cache improves latency and reduces backend load, but introduces freshness and invalidation trade-offs.\n\n[Back to Table of Contents](#table-of-contents)\n\n## 60. Database Performance from an API Perspective\n<a id="database-performance-from-an-api-perspective"></a>\n\nAPI performance often depends on database behavior.\n\nKnow:\n- indexes\n- query plans\n- connection pools\n- transactions\n- N+1 queries\n- pagination\n- batching\n\nExample: `GET /users` returning 10,000 rows is usually less practical than a paginated indexed query.\n\n[Back to Table of Contents](#table-of-contents)\n\n## 61. Distributed Systems Basics\n<a id="distributed-systems-basics"></a>\n\nA distributed system has multiple communicating components that can fail independently.\n\nReality:\n- networks are unreliable\n- messages can be delayed or duplicated\n- processes restart\n- partial failure exists\n- clocks differ\n\nThis explains timeouts, retries, idempotency, queues and tracing.\n\n[Back to Table of Contents](#table-of-contents)\n\n## 62. Replication and Consistency\n<a id="replication-and-consistency"></a>\n\nReplication means keeping copies of data on multiple nodes.\n\n**Read replica:** useful for scaling reads.\n\n**Strong consistency:** stronger guarantees about visibility/order of writes.\n\n**Eventual consistency:** replicas may temporarily differ and converge later.\n\n**Interview point:** choose consistency based on application requirements.\n\n[Back to Table of Contents](#table-of-contents)\n\n## 63. Partitioning and Sharding\n<a id="partitioning-and-sharding"></a>\n\nPartitioning divides data into smaller pieces; sharding distributes partitions across machines.\n\nStrategies:\n- range\n- hash\n- consistent hashing\n\nChallenges:\n- rebalancing\n- cross-shard queries\n- hotspots\n- distributed transactions\n\n[Back to Table of Contents](#table-of-contents)\n\n## 64. Messaging and Async Processing\n<a id="messaging-and-async-processing"></a>\n\nA queue lets producers submit work for workers to process later.\n\nExample:\n`FastAPI -> queue -> Celery worker -> image search`\n\nBenefits:\n- decoupling\n- asynchronous execution\n- buffering\n- retries\n\n[Back to Table of Contents](#table-of-contents)\n\n## 65. Queues vs Pub/Sub\n<a id="queues-vs-pubsub"></a>\n\n**Queue:** work is distributed among consumers.\n\n**Pub/Sub:** an event can be delivered to multiple subscribers.\n\nExample:\n`OrderCreated -> billing + analytics + notification`\n\n[Back to Table of Contents](#table-of-contents)\n\n## 66. Kafka vs RabbitMQ: Interview-Level View\n<a id="kafka-vs-rabbitmq-interview-level-view"></a>\n\n**RabbitMQ:** commonly used as a message broker with queues, acknowledgments, exchanges and routing.\n\n**Kafka:** distributed event streaming platform centered on topics, partitions, offsets, consumer groups and retention.\n\n**Interview line:** RabbitMQ is commonly used for task/message brokering, while Kafka is commonly used for durable event streams and high-throughput event processing.\n\nChoose by requirements; neither is universally better.\n\n[Back to Table of Contents](#table-of-contents)\n\n## 67. Maintenance, Refactoring and Technical Debt\n<a id="maintenance-refactoring-and-technical-debt"></a>\n\n**Refactoring:** improve internal structure without intentionally changing external behavior.\n\n**Technical debt:** future engineering cost caused by shortcuts, poor design or deferred work.\n\nMaintenance can be corrective, adaptive, perfective or preventive.\n\n[Back to Table of Contents](#table-of-contents)\n\n## 68. Backward Compatibility and Deprecation\n<a id="backward-compatibility-and-deprecation"></a>\n\nBackward compatibility means existing consumers continue to work.\n\nSafer API evolution often means:\n- add fields rather than remove them\n- keep old versions during migration\n- document deprecation timelines\n- provide migration guidance\n\n[Back to Table of Contents](#table-of-contents)\n\n## 69. Practical Engineering Workflow\n<a id="practical-engineering-workflow"></a>\n\n`Understand requirement -> clarify constraints -> design API -> choose architecture -> design data -> implement -> test -> review -> build -> deploy -> observe -> iterate`\n\nFor each component, think:\n- success\n- failure\n- retry\n- scale\n- testing\n- observability\n\n[Back to Table of Contents](#table-of-contents)\n\n## 70. SceneFlow Application\n<a id="sceneflow-application"></a>\n\nArchitecture:\n`React -> HTTPS -> FastAPI -> PostgreSQL/Redis -> Celery -> Gemini/image providers/Qdrant`\n\nInterview concepts:\n- REST APIs and Pydantic validation\n- CORS\n- PostgreSQL transactions\n- Redis\n- Celery for long-running work\n- external API timeouts/retries\n- idempotent job handling\n- polling for results\n- logs and request IDs\n- deployment and tests\n\nStrong answer:\n> The API should not perform expensive image-search and embedding work synchronously when that would create long request latency. It accepts the job, dispatches asynchronous processing and exposes job status/results.\n\n[Back to Table of Contents](#table-of-contents)\n\n## 71. URL Shortener Application\n<a id="url-shortener-application"></a>\n\nFlow:\n`Browser -> DNS -> TCP/TLS -> HTTP -> reverse proxy/load balancer -> FastAPI -> Redis/PostgreSQL -> redirect`\n\nConcepts:\n- REST endpoint\n- unique short-code generation\n- database uniqueness constraint\n- Redis lookup cache\n- atomic counter where appropriate\n- redirect response\n- rate limiting\n- idempotency for retry-sensitive creation\n- latency/error monitoring\n\nIf Redis is down, the application may fall back to the database with degraded cache performance. If the database is unavailable, the API should return an appropriate error rather than claim success.\n\n[Back to Table of Contents](#table-of-contents)\n\n## 72. ScoreHub Application\n<a id="scorehub-application"></a>\n\nArchitecture:\n`React -> FastAPI -> PostgreSQL`\n\nFor live updates:\n`Score update -> backend -> WebSocket clients`\n\nConcepts:\n- transactional score updates\n- concurrency control\n- validation\n- authorization\n- WebSockets\n- audit logs\n- integration tests\n- health checks\n- monitoring\n\n**Interview point:** polling is simpler but can create repeated traffic; WebSockets are useful for frequent real-time push updates.\n\n[Back to Table of Contents](#table-of-contents)\n\n## 73. Generic Interview Questions and Answers\n<a id="generic-interview-questions-and-answers"></a>\n\n### What is SDLC?\nSDLC is the lifecycle through which software is planned, developed, tested, deployed and maintained.\n\n### Agile vs Waterfall?\nWaterfall emphasizes sequential planning; Agile emphasizes iterative delivery and adaptation.\n\n### What is a non-functional requirement?\nA quality attribute or constraint such as latency, availability, security or scalability.\n\n### Monolith vs microservices?\nA monolith is one deployable application; microservices use multiple independently deployable services and introduce distributed-system complexity.\n\n### What is CI?\nFrequently integrating changes and automatically validating them with builds and tests.\n\n### What is technical debt?\nFuture engineering cost caused by shortcuts or deferred design/maintenance work.\n\n### What is observability?\nThe ability to investigate system behavior using telemetry such as logs, metrics and traces.\n\n[Back to Table of Contents](#table-of-contents)\n\n## 74. API Interview Questions and Answers\n<a id="api-interview-questions-and-answers"></a>\n\n### Is every API a REST API?\nNo. REST is one API style. APIs can also be SOAP, GraphQL, gRPC, WebSocket-based, webhook-based or in-process library interfaces.\n\n### REST vs GraphQL?\nREST commonly exposes resource-oriented endpoints. GraphQL commonly exposes a schema through which clients specify the fields they need.\n\n### REST vs gRPC?\nREST is common for broad HTTP-facing APIs. gRPC is useful for internal RPC with efficient serialization and generated clients.\n\n### When would you use WebSockets?\nFor ongoing, low-latency, bidirectional communication such as chat or live scores.\n\n### What is a webhook?\nA callback sent by one system to another when an event occurs.\n\n### Why is idempotency important?\nBecause clients may retry after timeouts, and idempotency prevents unintended duplicate effects.\n\n### 401 vs 403?\n`401` means valid authentication credentials are missing/invalid; `403` means access is not permitted.\n\n### Why paginate?\nTo limit response size, backend work and network transfer.\n\n### Why version an API?\nTo evolve contracts without unexpectedly breaking consumers.\n\n### What should an API error contain?\nA stable code, useful message, relevant details and optionally a correlation ID, without exposing sensitive internals.\n\n[Back to Table of Contents](#table-of-contents)\n\n## 75. Software Engineering Traps\n<a id="software-engineering-traps"></a>\n\nDo not say:\n- Microservices are always better.\n- JWT is always better than sessions.\n- REST is the only API.\n- SOAP is dead.\n- Retries are always good.\n- WebSockets are faster REST.\n- CORS secures the API.\n- Docker is the same as Kubernetes.\n- CI/CD always means automatic production deployment.\n- Unit tests are enough.\n\nInstead, explain the use case, trade-off and failure mode.\n\n[Back to Table of Contents](#table-of-contents)\n\n## 76. Interview Answer Framework\n<a id="interview-answer-framework"></a>\n\nUse:\n**Definition -> Purpose -> Simple example -> Practical project connection -> Trade-off**\n\nExample:\n> **What is gRPC?** gRPC is an RPC framework commonly using HTTP/2 and Protocol Buffers. It provides strongly typed contracts and generated clients, so it is useful for internal service-to-service communication. A trade-off is that browser-facing clients may find ordinary HTTP/JSON APIs easier to consume.\n\n[Back to Table of Contents](#table-of-contents)\n\n## 77.
